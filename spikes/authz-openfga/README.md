# OpenFGA authorization spike

Throwaway Gate 0 spike for [ADR 0004](../../docs/adr/0004-authorization-engine.md). It runs the Tickets permission model on OpenFGA through the official .NET SDK, and checks the SQL list-filter plan against Postgres.

## Contents

| Path | What |
|---|---|
| `model/tickets.fga` | The fixed platform model, written in the OpenFGA DSL (schema 1.1, with one CEL condition) |
| `model/tickets.json` | The same model as JSON, generated by `fga model transform`. The app loads this file |
| `model/tickets.fga.yaml` | Model tests for `fga model test` (4 tests, 13 checks, 1 ListObjects; all pass) |
| `src/Authz.cs` | `IAuthorizationEngine` port, the OpenFGA adapter that fails closed, and `TicketRow` → contextual tuples |
| `src/SqlListFilter.cs` | Compiles a principal's access into a SQL predicate, plus Postgres seeding and conformance helpers |
| `src/Program.cs` | The scenarios. Each assertion prints PASS or FAIL, followed by timing metrics |

## How to run

```bash
export PATH=/root/.dotnet:$PATH DOTNET_CLI_TELEMETRY_OPTOUT=1
docker run -d --rm --name fga-spike -p 18080:8080 -e OPENFGA_LOG_LEVEL=warn openfga/openfga:latest run
docker run -d --rm --name pg-authz-spike -e POSTGRES_PASSWORD=spike -p 15432:5432 postgres:18-alpine
cd spikes/authz-openfga/src
dotnet run -- --pg "Host=localhost;Port=15432;Username=postgres;Password=spike" --tickets 500000 --docker-pause fga-spike
docker stop fga-spike && dotnet run -- --fail-closed-only      # stopped engine => deny
docker stop pg-authz-spike
# model tests / DSL -> JSON
docker run --rm -v $PWD/../model:/m -w /m openfga/cli model test --tests tickets.fga.yaml
docker run --rm -v $PWD/../model:/m openfga/cli model transform --file /m/tickets.fga > ../model/tickets.json
```

Flags: `--fga <url>` sets the engine URL (default `http://localhost:18080`). `--pg <conn>` turns on the SQL conformance and list timings. `--docker-pause <name>` runs the hung-engine test.

To run against the Postgres datastore, first create a database and run `openfga migrate --datastore-engine postgres --datastore-uri ...`. Then start the server with `OPENFGA_DATASTORE_ENGINE=postgres`. To add the check cache, also set `OPENFGA_CHECK_QUERY_CACHE_ENABLED=true` and `OPENFGA_CHECK_QUERY_CACHE_TTL=10s`.

## Design exercised

- **Stored tuples** are group memberships (nested `group#member`), role assignments (to users or groups), and tenant policy grants, which the platform would compile from versioned permission-set specs.
- **Record attributes are never stored.** The kernel reads requester, assignee, watchers, owner_group and entity from the ticket row and sends them as contextual tuples on every Check. Priority goes in the Check `context`, where the CEL condition reads it.
- **ABAC:** `entity_type:ticket#priority_editor` holds `user:*` with the condition `not_major_incident(priority != 1)`, plus `role:major_incident_manager#assignee`. `can_edit = editor_base and priority_editor from entity`.
- **Field and action level:** `field:ticket.internal_cost#reader` is granted to `role:finance#assignee`. `tenant:<id>#config_publish` and `#permissions_admin` are separate relations granted to separate roles.
- **AI agents:** the PDP sends one BatchCheck of 3 checks: the user's permission, the agent's delegated scope (`agent_read_scope` / `agent_edit_scope`), and `acts_for` delegation. The request is allowed only when all three are true.
- **Tenant isolation:** each tenant-environment gets its own store with a pinned model id. One `OpenFgaClient` serves all stores, using the per-request `StoreId` and `AuthorizationModelId` options.
- **Lists:** `ListObjects(user, member, group)` plus a BatchCheck of `read_all`, `edit_all`, and `priority_editor` for each enumerable priority value is compiled into a SQL `WHERE` clause. A conformance check then compares engine Check results with the SQL filter on sampled rows.

## Results observed (2026-10-10)

Environment: OpenFGA v1.22.0 in Docker, `postgres:18-alpine`, and OpenFga.Sdk 0.10.4 on .NET 10.0.401. The host is a 4-vCPU sandbox VM, and other workloads (concurrent `rustc` builds) were competing for CPU during the runs. Treat the numbers as rough upper bounds, not capacity planning.

### Functional: 49/49 PASS (memory datastore, 500k tickets)

All scenarios passed: record-level view and edit for 9 principals, nested groups, roles assigned to groups, no stored record tuples, the CEL priority guard, field-level, action-level, AI-agent intersection, tenant isolation, contextual-tuple limits, revocation, SQL conformance, and fail closed. The same suite also passed against a Postgres-datastore server, with and without the check cache (46/46 and 48/48; those runs skip the SQL part).

### Latency (sequential, mean / p95 in ms, includes the HTTP round trip)

| Operation | Memory store | Postgres store | Postgres + check cache |
|---|---|---|---|
| Check `can_view`, nested group via contextual `owner_group` (1000 checks) | 6.7 / 13.3 | 6.5 / 10.5 | 1.7 / 2.5 |
| Same Check with the record tuples **stored** instead of contextual | 5.9 / 12.2 | 7.4 / 13.3 | 1.2 / 1.7 |
| Check `can_view`, direct requester | 2.2 / 5.6 | 3.1 / 6.0 | 1.6 / 2.5 |
| Check `can_edit` P1 with CEL (MIM) | 2.3 / 4.6 | 4.3 / 6.7 | 1.3 / 1.7 |
| ListObjects(user, member, group), 2 groups | 1.3 / 1.9 | 2.9 / 4.1 | 3.0 / 5.4 |
| ListObjects, 40 groups (20 nested) | 1.8 / 2.2 | 4.2 / 5.6 | 4.3 / 6.2 |
| Compile SQL filter (ListObjects + BatchCheck of 6) | 3.7 / 5.1 | 9.5 / 15.6 | 4.9 / 7.8 |
| BatchCheck of 50 rows (one page) | 194 / 264 | 368 / 643 | 22 (one cold outlier) / 14 |
| 5000 Checks at concurrency 32: throughput | 126/s | 81/s | 3127/s |
| CreateStore + WriteAuthorizationModel (100 stores) | 6.8 / 13.3 | 9.0 / 11.0 | 8.9 / 11.3 |

Takeaways:

- **Contextual tuples cost nothing measurable** compared with stored tuples. Dual-writing record tuples is therefore not needed for Check.
- **Uncached throughput is CPU-bound on this host.** OpenFGA used about 11 ms of CPU per nested Check, and about 3 ms even for a trivial Check or Read, served over the HTTP/JSON gateway. Raw `curl` showed the same cost, so the SDK is not the cause. The SpiceDB spike reached 1.9 ms mean over gRPC on the same host.
- **Production needs dedicated CPU and the check cache, and should benchmark again on real hardware.** BatchCheck runs its items server-side, so it is no faster than N single Checks when uncached.
- **Store creation is cheap:** about 7–9 ms per tenant-environment.

**Conformance:** engine Check matched the SQL predicate in all 10,656 (user, relation, row) cases, with 0 mismatches. That covers 9 users × {can_view, can_edit} × 592 sampled rows. Seeding 600k rows took 8.9 s.

alice's sparse-match first page (19 ms) walks the `updated_at` index. The real query layer needs planner care here, for example a `UNION` of the indexed branches.

### Revocation and consistency

- Deleting `group:network-team#member → group:l1-support` and then running a Check with `HIGHER_CONSISTENCY` returned **deny right away**: 10–14 ms for the delete and check together. ListObjects shrank on the same call.
- With `MINIMIZE_LATENCY` and the check cache on (TTL 10s), the read right after the delete also returned deny in this run. We do not rely on that: the ADR bounds staleness by the cache TTL and uses `HIGHER_CONSISTENCY` for sensitive actions.

### Fail closed

| Case | Raw SDK behaviour | PDP decision |
|---|---|---|
| Endpoint down or container stopped | `System.Net.Http.HttpRequestException` (inner `SocketException`, connection refused), surfaced after about 1 s | Deny(`EngineUnavailable`) |
| Engine hung (`docker pause`) | `TaskCanceledException` at `HttpClient.Timeout` (2 s here) | Deny(`EngineUnavailable`) |
| 4xx (bad model id, missing condition parameter, >100 contextual tuples) | `FgaApiValidationError` (`StatusCode`, `ApiError.ErrorCode`) | Deny(`EngineError`) |
| List compile while the engine is down | Exception propagates | No list is served |

## .NET SDK notes (OpenFga.Sdk 0.10.4)

- **Package:** `OpenFga.Sdk` 0.10.4, owned by `openfga`, 3.9M downloads, published 2026-07-20. It targets net8.0, net9.0, netstandard2.0 and net48 (no net10.0 TFM, but it works on net10). It has no third-party dependencies.
- **Client:** construct with `new OpenFgaClient(new ClientConfiguration { ApiUrl, RetryParams = new RetryParams { MaxRetry, MinWaitInMs } }, httpClient)`. It is HTTP/JSON only, with no gRPC client. Set the timeout on the `HttpClient` you pass in.
- **Per-request store and model:** set `StoreId` and `AuthorizationModelId` on `ClientCheckOptions`, `ClientBatchCheckOptions`, `ClientListObjectsOptions`, `ClientWriteOptions` and `ClientReadOptions`. This lets a single client serve every tenant store.
- **Check:** `client.Check(new ClientCheckRequest { User, Relation, Object, ContextualTuples = List<ClientTupleKey>, Context = IDictionary<string, object> }, new ClientCheckOptions { Consistency = ConsistencyPreference.HIGHERCONSISTENCY })`. It returns `CheckResponse.Allowed` as a `bool?`.
- **BatchCheck (server-side):** `client.BatchCheck(new ClientBatchCheckRequest { Checks = List<ClientBatchCheckItem> }, ClientBatchCheckOptions)`. Each item takes `ContextualTuples = new ContextualTupleKeys(List<TupleKey>)`, a different type from Check's `List<ClientTupleKey>`, plus `CorrelationId`. Results come back in `Result[]` with `Allowed`, `CorrelationId` and `Error`. `ClientBatchCheck` is the older client-side fan-out.
- **ListObjects:** `client.ListObjects(new ClientListObjectsRequest { User, Relation, Type }, ClientListObjectsOptions)` returns `.Objects` as a `List<string>` of `type:id`. `StreamedListObjects` also exists.
- **Writes:** `client.Write(new ClientWriteRequest(writes, deletes), new ClientWriteOptions { ... })`. Conditional tuples use `Condition = new RelationshipCondition { Name, Context }`, and `WriteTuples` / `DeleteTuples` are convenience wrappers.
- **Model:** `JsonSerializer.Deserialize<ClientWriteAuthorizationModelRequest>(json)` works directly on the CLI's JSON output. There is no DSL parser for .NET, so DSL → JSON must happen at build time with the `fga` CLI (Go binary or the `openfga/cli` image).

Gotchas:

1. **Writes over 100 tuples are rejected.** The error is `FgaApiValidationError: The number of write operations exceeds the allowed limit of 100`. Use `Transaction = new TransactionOptions { Disable = true, MaxPerChunk = 100 }`, but each chunk is then its own transaction.
2. **Contextual tuples are capped at 100 per Check** (`invalid ContextualTupleKeys.TupleKeys`). Watchers must be capped, or the watcher test moved into the kernel or SQL.
3. **A missing condition parameter returns HTTP 400, not `allowed=false`,** when the evaluation reaches the conditional tuple. The PDP must always send every attribute the policy references.
4. **Network failures surface after about 1 s** whatever the `RetryParams` setting: raw `HttpClient` fails in about 1 ms, but the SDK took about 1 s even with `MaxRetry=0`. Wrap calls in a per-call `CancellationToken` deadline and a circuit breaker so the PDP fails fast.
5. **The default image logs every request at INFO** with the full raw request. Run with `OPENFGA_LOG_LEVEL=warn` for anything performance-related.
6. **Model ids belong to one store.** Using tenant A's model id against tenant B's store returns `authorization_model_not_found`, which is a useful extra isolation guard.
