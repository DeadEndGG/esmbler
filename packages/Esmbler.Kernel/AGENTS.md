# Esmbler.Kernel

Pure kernel logic (no database or network): configuration composition/validation/compilation, record contract (normalization, write pipeline), policy decision point, request context, ports.

- Owns: `Configuration/` (Composer, ConfigValidator, DependencyGraph, ConfigCompiler, PlatformModule), `Records/` (FieldNormalizer, RecordWriteEngine, `IRecordWriteHook`), `Authorization/` (EffectivePermissions, `IRelationshipGraph`, in-memory fake), `Tenancy/RequestContext`.
- Approvals (ADR 0016): the composer applies `approval_policy.*` ops and catalog item `approvalPolicy`; `ConfigValidator` checks policies, approvers, stage conditions, the request entity's approval binding (request/approved/declined transitions, a read-only `principals` approvers field that should be a non-editable access field) and refuses workflow migrations that would strand pending approvals (`config.strands_approvals`). Access fields of type `principals` match the caller or their groups in `EffectivePermissions`; keep the SQL filter in `Esmbler.Kernel.Infrastructure/Records/QueryCompiler.cs` in step.
- Events (ADR 0017): `PlatformModule.EventTypes` are built in (added by `Composer.ComposeBase`, ASM-051); `ConfigValidator` checks event types (namespaces, severity, sensitivity, payload fields) and emits (known type, not a platform type, same subject entity, required and declared fields, plain-field types, no hidden fields unless restricted, data rules only); `Records/EventEmission` evaluates emits with type checks and text caps. Tenants may add emits to module transitions, never remove the module's (composer).
- SLAs (ADR 0018): `Sla/BusinessTime` (business-time arithmetic, DST rules) and `Sla/SlaEngine` (pure timer state machine: existing timers follow their snapshot, new ones the current policy); `ConfigValidator` checks calendars (IANA zone, hours, overlaps, holidays) and SLA policies (targets, conditions, goals, calendars).
- Metrics (ADR 0019): `ConfigValidator.ValidateMetric` checks measures, groupable types (`IsGroupable`), date ranges (at most 52 buckets), groups (1–25), SLA conditions, roles and format, and warns `metric.restricted_field` when a metric reads a field some permission set hides; dashboard views hold only `layout.*` and `display.*` nodes and tiles must match grouped or ungrouped metrics. Metric filters must pass `Records/QueryFilterSupport` (the subset `QueryCompiler` turns into SQL); keep it in step with `Esmbler.Kernel.Infrastructure/Records/QueryCompiler.cs`. `Metrics/DateBuckets` builds rolling windows and buckets (weeks start Monday, the current partial unit included, DST-correct local midnights). `ConfigCompiler.PermissionDiff` reports a metric `roles` change as a permission change (it gates who sees the figure). `DependencyGraph` has metric edges; `ConfigDiff` covers metrics, SLA policies, calendars, catalog items, approval policies and event types.
- Notifications (ADR 0021): `PlatformModule.NotificationProfiles` (`core.platform.profile.in_app`, `.in_app_email`, `.urgent`) are built in like event types (`Composer.ComposeBase`). `ConfigValidator.ValidateNotifications` checks templates (plain text, no HTML, known placeholders `{{record.<field>}}`, `{{record.number}}`, `{{event.<field>}}`, `{{recipient.name}}`, `{{link}}`, `{{activity.body}}` (public reply text, ADR 0023), 4,000 characters, known variant channels and external fields; legacy templates with an `Event` need an entity and user or email recipients), subscriptions (known event type, `notify` target, condition compiled against `EntitySchema.ForSubscription`; `config.notification_hidden_field` when it reads a field any permission set hides; `config.restricted_event_text` when it reads `event.*` of a restricted event type), profiles (distinct known channels, `all` or `fallback`, severity) and routes (known subscription, profile and a template without its own trigger for the same entity; 1 to 50 recipient rules of known kinds; `config.external_redaction` for external recipients (`IsExternalRecipient`: addresses and `field` rules over email fields) on non-public events; `config.restricted_event_text` when the template renders `{{event.*}}` for a restricted event; `config.mandatory_unreachable` when a mandatory route's subscription, template or profile is disabled or its profile lacks `in_app`; `config.foreign_notification_element` (`ValidateNotificationOwnership`) when a module-layer element is outside the module's namespace or a module route uses another module's subscription, template or profile; only its own and `core.platform`'s are allowed, not those of declared dependencies). The composer applies the 12 notification ops: tenant objects only are removable and only when unused; module subscriptions keep their condition, module routes their recipients and mandatory flag, and a mandatory route cannot be turned off (`overlay.mandatory`). `ConfigCompiler.PermissionDiff` flags mandatory-flag and external-recipient changes on routes (email-field recipients count as external) and `ExternalFields` changes on templates, and for mandatory routes and routes with external recipients compares a reach signature (`Reach`: recipients, enabled, subscription event/entity/condition/enabled, template text/variants/external fields/enabled, profile channels/delivery/minimum severity/enabled, and the rules and transitions that emit the event); keep `Reach` in step when these specs gain properties that change who is told or what; `DependencyGraph` and `ConfigDiff` cover all four objects. `EffectivePermissions` strips `notifications.manage` from agents.
- Alerts (ADR 0022): `ConfigValidator.Alerts.cs` (`ValidateAlertRules`) checks rules: trigger and resolving subscriptions exist and have target `alert` (`config.bad_target`; routes must use `notify` ones), no trigger on `platform.alert.*` (`config.alert_loop`), the key compiles against the trigger (and against resolving events about no record) (`config.alert_bad_dedup`), title, key and owner field read no field any permission set hides (`config.alert_hidden_field`) and no restricted event values (`config.restricted_event_text`), plain-text titles with known placeholders up to 200 characters, owners (`config.alert_bad_owner`), escalation steps and cool-down (`config.alert_bad_escalation`), severities (`config.bad_severity`); `alert_owner` recipients only on alert events; module rules stay in their namespace and use only their own subscriptions (`ValidateNotificationOwnership`). The composer applies `alert_rule.*` (tenant IDs for add; module rules keep `Trigger` and `DedupKey`; only tenant rules removable; a subscription a rule uses cannot be removed). `PlatformModule.EventTypes` holds the five `platform.alert.*` types. `Alerts/AlertLifecycle.cs` is the pure state machine and escalation timing (levels, at most 20 repeats, `UnlessAcknowledged`, cool-down). `ConfigCompiler.PermissionDiff` adds `AlertReach` to the reach signature of routes on alert events (every rule's ID, enabled, trigger, severities, escalation, resolving subscriptions, owner, and the trigger subscription's event, condition and enabled); keep it in step when `AlertRuleSpec` gains properties that change whether or when an alert is raised. `DependencyGraph` and `ConfigDiff` cover alert rules. `EffectivePermissions` strips `alerts.respond`, `alerts.manage`, `audit.export` and `audit.manage` from agents.
- Mail (ADR 0023): `ConfigValidator.Mail.cs` (`ValidateMailIntakes`) checks intakes: known entity, field types (title short or long text, body long or rich text, requester user, address email; `config.mail_bad_field`), constants only on choice, text or toggle fields (never people, groups, numbers, status, system or the requester field), known reopen transition and states, no state in both `ReopenFrom` and `FollowUpFrom` (`config.mail_reopen`); module intakes stay in their namespace and use their own entities (`ValidateNotificationOwnership`). `Composer`, `DependencyGraph` (`mail_entity`, `mail_field`, `mail_workflow`) and `ConfigDiff` (`mail_intake`) cover intakes. There are no `mail_intake.*` overlay ops yet (KI-047); when added, `Set` and `RequesterField` changes must be permission changes in `PermissionDiff`.
- Extension points: `IRecordWriteHook` (platform services plug in: workflow 100, requests 150, assignment 200, rules 300). `RecordWriteEngine.PrepareAsync` takes the record's pinned workflow version and a system-actor flag (ADR 0015).
- Invariants: knows no business module; no Npgsql/EF/OpenFGA (architecture test); every validation message says what, where, and how to fix.
- Tests: `dotnet test tests/Esmbler.UnitTests`.
