# Esmbler.Kernel.Infrastructure

Adapters and application services for the kernel: PostgreSQL (EF Core + Npgsql), SQL migrations, RLS unit of work, OpenFGA, record/config/draft/publish/upgrade/preview services, activation health check, workflow definition versions (`Configuration/WorkflowVersions.cs`), outbox dispatcher (per-consumer transactions, `kernel.consumer_failures`, retention through `kernel.purge_outbox`), `Events/EventWriter.cs` (every outbox write: envelope v2, legacy reads), job runner and job handlers (`upgrade.run`, `workflow.migrate`, `approval.expire`, `sla.check`, `notify.resolve`, `notify.deliver`), event consumers (record projection, the notification `SubscriptionRouter` and legacy `NotificationConsumer`, fulfillment, approvals), the notification service (`Notifications/`, ADR 0021), and the approval engine (`Approvals/ApprovalService.cs`, `Approvals/ApprovalConsumer.cs`, ADR 0016).

- Data access only through `Persistence/Database` (`InTenantAsync`, `InTenantWideAsync`, `AsPrincipalAsync`, `AnonymousAsync`), which sets `app.tenant_id`/`app.environment_id`/`app.principal_id` transaction-locally.
- Migrations: `Migrations/NNNN_*.sql`, applied by `MigrationRunner` as `esmbler_migrator`; never edit applied files.
- Authorization store: one OpenFGA store per tenant, model `Authorization/platform-model.fga(.json)`; derived from `kernel.group_members`/`kernel.role_assignments`. `AccessService` caches facts per (tenant, principal, `authz_revision`) for 5 s; sensitive actions (publish, rollback, modules, permission admin) and job re-authorization pass `fresh: true`.
- Activation (`ConfigActivator`) runs `ActivationHealthCheck` inside the activation transaction; a failure rolls the revision back. It also registers workflow definition versions (`kernel.workflow_definitions`) and schedules `workflow.migrate` when a changed workflow's policy is migrate or cancel.
- Approvals: every decision, expiry or cancellation first locks the request row; decisions refuse agent contexts, the requester (also through delegates) and a second decision by one person in a stage; approvals run on their policy snapshot; the request moves only through the binding's system transitions (`RecordService.SystemWriteAsync`); approvers get read access through the request's `principals` approvers field, which only the platform writes. `kernel.approval*` rows are never deleted.
- SLAs (ADR 0018): `Sla/SlaService.ApplyAsync` runs inside every record write transaction (after the record row is written, while it is locked) and `CancelAsync` on delete; `kernel.sla_timers` rows are never deleted and keep their snapshot; the `sla.check` job completes itself before scheduling the next check (the scheduler cannot move a running job).
- Metrics (ADR 0019): `Records/QueryCompiler.Where` is the one WHERE clause for lists, explorer group counts and metrics (permission predicate inside SQL, SLA breach conditions, search); never build a separate query path for figures, or figures and the explorer stop agreeing. `Metrics/MetricService` evaluates figures in the tenant transaction, each in a savepoint under a 5 s statement timeout within an overall request budget (`MetricService.RequestBudget`, 8 s; figures not reached report `timeout`), returns a `DrillQuery` per figure, bar and row (date windows as absolute instants), and computes nothing for restricted metrics (roles, hidden fields, no `records:read`; dashboard data leaves them out). `QueryCompiler.MaxCount` caps explorer totals, figures, bars, rows and group headers alike (each with its own `Capped` flag). `ExperienceService` removes restricted tiles and metric saved views, prunes data-table `groupBy`/`groupOptions` on fields hidden from the viewer, and lists visible dashboards in the bootstrap.
- Draft change sets (REQ-WS-005): `DraftService.ApplyBatchAsync` validates and records several ops as one change (`kernel.draft_commands.batch_id`, migration 0011): all or none, one version. `ApplyAsync` is a batch of one. `SetUndoneAsync` undoes or redoes one step, or the whole batch with `wholeChange: true` (REQ-LIVE-003, ASM-065); it requires `permissions.admin` to undo or redo any step of a batch that contains a permission-affecting op (it checks the whole batch, so such a change is never split), as applying it does.
- Workspace creation (ADR 0020): `Services/WorkspaceService` lists starters with the surfaces generated from each module's latest release and creates a workspace through `ProvisioningService` (`TenantSeed.CreatedBy` and `CreationLimit`, `SampleData: false`; the creator as `UserSeed.Principal` from the session, tenant administrator); the tenant row goes through `kernel.create_workspace` (migrations 0012 and 0013), which fails closed on missing arguments, accepts only an enabled `kind = 'user'` creator (otherwise `42501`, turned into 403), enforces the per-person limit under an advisory lock and inserts the tenant as `provisioning`; after provisioning and the audit `workspace.create`, `kernel.activate_workspace` makes it `active`. Only active tenants are listed or switchable (`IdentityService.TenantsForAsync`). Names and answers lose control and format characters. Never take the creator from request data. `MetricService.DashboardAsync` returns preview figures (`DashboardData.Empty`, `MetricResult.Preview`, no drill) only when the viewer can see no records of the dashboard's entity; that check runs within the request budget in a savepoint, and on timeout the real figures are shown; previews never read records.
- Notifications (ADR 0021): `Notifications/NotificationJobs.cs` holds `SubscriptionRouter` (event consumer; schedules one `notify.resolve` job per matching subscription, dedup `notify:{event}:{subscription}`, never sends), `NotifyResolveJobHandler` (routes in order mandatory, tenant, module; recipients must be enabled members who may read the record; mutes except on mandatory routes; one `kernel.notification_deliveries` row per recipient and channel with the unique idempotency key `{event}:{principal or address}:{channel}`; text rendered once by `NotificationRenderer` under the recipient's permissions, external recipients only `ExternalFields` and public payloads; at most `MaxRecipientsPerEvent` deliveries, audited `notification.recipients_capped`) and `NotifyDeliverJobHandler` (locks the row; in-app writes `kernel.notifications`; capture and disabled instances never call a provider; per-instance rate; transient retries; `unknown` is retried only when the adapter `SupportsIdempotency`, otherwise `ambiguous`, as is a row found in `sending`; attempts are appended to `kernel.notification_delivery_attempts`; never log adapter exceptions). `NotificationService` serves the inbox and preferences (the signed-in person only; agents refused), channel instances (`notifications.manage` or `permissions.admin` with fresh facts; secret-like settings refused; live needs an allow-listed host and, outside production, `permissions.admin`), delivery inspection (text only for managers; `audit.read` sees status), audited replay (failed and ambiguous requeue; sent only with `force`, as a new delivery) and test sends, and previews that write nothing (recipient ∩ viewer). Channel adapters (`Channels/SmtpEmailChannel.cs` with MailKit, `Channels/HttpSmsChannel.cs`) re-check the host allow-list on every send and read credentials only through `ISecretStore` (`EnvironmentSecretStore`: `ESMBLER_SECRET__<slug>__<NAME>`). Channel instances are environment settings: never put them in artifacts or copy them between environments. MailKit and MimeKit stay in this project (architecture test).
- Events (ADR 0017): publish only through `EventWriter` in the caller's transaction; each consumer runs in its own tenant transaction and must be idempotent (inbox); a consumer that keeps failing dead-letters alone (queue `consumers` in `OperationsService`).
- Invariants: record change + audit + outbox in one transaction; queries filter by permission inside SQL; no secrets in audit details.
- Tests: `dotnet test tests/Esmbler.IntegrationTests` (needs Docker).
