# Esmbler.Kernel.Infrastructure

Adapters and application services for the kernel: PostgreSQL (EF Core + Npgsql), SQL migrations, RLS unit of work, OpenFGA, record/config/draft/publish/upgrade/preview services, activation health check, workflow definition versions (`Configuration/WorkflowVersions.cs`), outbox dispatcher (per-consumer transactions, `kernel.consumer_failures`, retention through `kernel.purge_outbox`), `Events/EventWriter.cs` (every outbox write: envelope v2, legacy reads), job runner and job handlers (`upgrade.run`, `workflow.migrate`, `approval.expire`, `sla.check`, `notify.resolve`, `notify.deliver`, `alert.evaluate`, `alert.escalate`, `alert.unsuppress`, `mail.process`), event consumers (record projection, the notification `SubscriptionRouter`, the `AlertRouter` and legacy `NotificationConsumer`, fulfillment, approvals), the notification service (`Notifications/`, ADR 0021), alerts (`Alerts/`, ADR 0022), the audit services (`Services/AuditService.cs`, `Services/AuditMaintenance.cs`, ADR 0022), email intake (`Mail/`, ADR 0023), AI provider settings (`Assistant/`, ADR 0024), and the approval engine (`Approvals/ApprovalService.cs`, `Approvals/ApprovalConsumer.cs`, ADR 0016).

- Data access only through `Persistence/Database` (`InTenantAsync`, `InTenantWideAsync`, `AsPrincipalAsync`, `AnonymousAsync`), which sets `app.tenant_id`/`app.environment_id`/`app.principal_id` transaction-locally.
- Migrations: `Migrations/NNNN_*.sql`, applied by `MigrationRunner` as `esmbler_migrator`; never edit applied files.
- Authorization store: one OpenFGA store per tenant, model `Authorization/platform-model.fga(.json)`; derived from `kernel.group_members`/`kernel.role_assignments`. `AccessService` caches facts per (tenant, principal, `authz_revision`) for 5 s; sensitive actions (publish, rollback, modules, permission admin) and job re-authorization pass `fresh: true`.
- Activation (`ConfigActivator`) runs `ActivationHealthCheck` inside the activation transaction; a failure rolls the revision back. It also registers workflow definition versions (`kernel.workflow_definitions`) and schedules `workflow.migrate` when a changed workflow's policy is migrate or cancel.
- Approvals: every decision, expiry or cancellation first locks the request row; decisions refuse agent contexts, the requester (also through delegates) and a second decision by one person in a stage; approvals run on their policy snapshot; the request moves only through the binding's system transitions (`RecordService.SystemWriteAsync`); approvers get read access through the request's `principals` approvers field, which only the platform writes. `kernel.approval*` rows are never deleted.
- SLAs (ADR 0018): `Sla/SlaService.ApplyAsync` runs inside every record write transaction (after the record row is written, while it is locked) and `CancelAsync` on delete; `kernel.sla_timers` rows are never deleted and keep their snapshot; the `sla.check` job completes itself before scheduling the next check (the scheduler cannot move a running job).
- Metrics (ADR 0019): `Records/QueryCompiler.Where` is the one WHERE clause for lists, explorer group counts and metrics (permission predicate inside SQL, SLA breach conditions, search); never build a separate query path for figures, or figures and the explorer stop agreeing. `Metrics/MetricService` evaluates figures in the tenant transaction, each in a savepoint under a 5 s statement timeout within an overall request budget (`MetricService.RequestBudget`, 8 s; figures not reached report `timeout`), returns a `DrillQuery` per figure, bar and row (date windows as absolute instants), and computes nothing for restricted metrics (roles, hidden fields, no `records:read`; dashboard data leaves them out). `QueryCompiler.MaxCount` caps explorer totals, figures, bars, rows and group headers alike (each with its own `Capped` flag). `ExperienceService` removes restricted tiles and metric saved views, prunes data-table `groupBy`/`groupOptions` on fields hidden from the viewer, and lists visible dashboards in the bootstrap. Who may see a figure is `Esmbler.Kernel.Metrics.MetricVisibility.Restricted` (`MetricService.Restricted` delegates). Since G2-M9c: SLA conditions take `at_risk` (open timer, warning recorded, no breach); grouped figures add an "Other" bucket only through an explorer filter (`MetricService.OtherFilter`; left out when it would exceed 1,000 characters); alert metrics (`MetricSpec.Alerts`, `EvaluateAlertsAsync`) join `kernel.alerts` to `kernel.records` under `QueryCompiler.Where` for the viewer and apply the Alerts page's visibility (keep it in step with `AlertService.Visible`; agents see only their own), never count suppressed alerts and carry no drill. Exports (`Records/RecordService.Export.cs`, `MetricService.ExportCsvAsync`) need `records.export` with fresh facts, refuse agents, audit before writing (`records.export`, `metric.export`), cap at `QueryCompiler.MaxCount`, write only visible fields, and escape cells with `Services/CsvText`. The dashboard builder (`Configuration/DashboardBuilderService.cs`) only applies draft batches (`view.add`, `view.remove`, `metric.add`, node ops from `Kernel.Configuration.DashboardLayout`) and passes the caller's source (`ui` or `mcp`).
- Draft change sets (REQ-WS-005): `DraftService.ApplyBatchAsync` validates and records several ops as one change (`kernel.draft_commands.batch_id`, migration 0011): all or none, one version. `ApplyAsync` is a batch of one. `SetUndoneAsync` undoes or redoes one step, or the whole batch with `wholeChange: true` (REQ-LIVE-003, ASM-065); it requires `permissions.admin` to undo or redo any step of a batch that contains a permission-affecting op (it checks the whole batch, so such a change is never split), as applying it does.
- Workspace creation (ADR 0020): `Services/WorkspaceService` lists starters with the surfaces generated from each module's latest release and creates a workspace through `ProvisioningService` (`TenantSeed.CreatedBy` and `CreationLimit`, `SampleData: false`; the creator as `UserSeed.Principal` from the session, tenant administrator); the tenant row goes through `kernel.create_workspace` (migrations 0012 and 0013), which fails closed on missing arguments, accepts only an enabled `kind = 'user'` creator (otherwise `42501`, turned into 403), enforces the per-person limit under an advisory lock and inserts the tenant as `provisioning`; after provisioning and the audit `workspace.create`, `kernel.activate_workspace` makes it `active`. Only active tenants are listed or switchable (`IdentityService.TenantsForAsync`). Names and answers lose control and format characters. Never take the creator from request data. `WorkspaceService.Personas` compiles a starter's latest release in memory and describes each role with `EffectivePermissions` and `MetricVisibility` (no records read, nothing created). `MetricService.DashboardAsync` returns preview figures (`DashboardData.Empty`, `MetricResult.Preview`, no drill) only when the viewer can see no records of the dashboard's entity; that check runs within the request budget in a savepoint, and on timeout the real figures are shown; previews never read records.
- Notifications (ADR 0021): `Notifications/NotificationJobs.cs` holds `SubscriptionRouter` (event consumer; schedules one `notify.resolve` job per matching subscription, dedup `notify:{event}:{subscription}`, never sends), `NotifyResolveJobHandler` (routes in order mandatory, tenant, module; each route's targets cut to `MaxRecipientsPerEvent` before permission checks; recipients must be enabled members who may read the record; mutes except on mandatory routes; one `kernel.notification_deliveries` row per recipient and channel with the unique idempotency key `{event}:{principal or address}:{channel}`, except that a mandatory route takes over a `suppressed`/`muted` row another subscription's route wrote for the same key; text rendered once by `NotificationRenderer` under the recipient's permissions: `{{event.*}}` blank for restricted events (a missing sensitivity counts as restricted), external recipients only `ExternalFields`, public payloads and `{{record.number}}` only if the auto-number field is external; at most `MaxRecipientsPerEvent` deliveries, audited `notification.recipients_capped`) and `NotifyDeliverJobHandler` (locks the row; re-checks a person recipient before sending (enabled user, member, can read the record under the published configuration with fresh facts; otherwise `suppressed`/`no_longer_authorized`) and sends email to their current address; in-app writes `kernel.notifications`; capture and disabled instances never call a provider; per-instance rate decided under a `pg_advisory_xact_lock` per tenant, environment and instance, counting messages in `sending`; transient retries; `unknown` is retried only when the adapter `SupportsIdempotency`, otherwise `ambiguous`, as is a row found in `sending`; when retries run out a `sending` row becomes `ambiguous` (`interrupted`) and a `queued` one `failed`; attempts are appended to `kernel.notification_delivery_attempts`; never log adapter exceptions). `NotificationService` serves the inbox and preferences (the signed-in person only; agents refused), channel instances (`notifications.manage` or `permissions.admin` with fresh facts; secret-like settings refused; `usernameRef`, `passwordRef` and `tokenRef` must name a declared secret reference; live needs an allow-listed host and, outside production, `permissions.admin`), delivery inspection (subject and body only for `permissions.admin`; `notifications.manage` alone and `audit.read` see status), audited replay (failed and ambiguous requeue, but an ambiguous delivery on a channel without idempotency needs `force`; sent only with `force`, as a new delivery; never `suppressed` as `muted` or `no_longer_authorized`, even forced) and test sends, and previews that write nothing (judged on the published configuration with the caller's real context; recipient ∩ viewer; recipient rules on fields hidden from the caller left out; suppressed recipients show "not sent" with no text or reason). Channel adapters (`Channels/SmtpEmailChannel.cs` with MailKit, `Channels/HttpSmsChannel.cs`) re-check the host allow-list on every send and read credentials only through `ISecretStore.For(slug, environmentKey)` (`EnvironmentSecretStore`: `ESMBLER_SECRET__<WORKSPACE_SLUG>__<ENVIRONMENT_KEY>__<NAME>`, upper-cased, hyphens as underscores; names without `__`); SMTP never sends unauthenticated when credentials are missing (`credentials_missing`) unless the instance's `auth` setting is `none`. Channel instances are environment settings: never put them in artifacts or copy them between environments. MailKit and MimeKit stay in this project (architecture test).
- Alerts (ADR 0022): `Alerts/AlertJobs.cs` holds `AlertRouter` (consumer `alerts.router`, ignores `platform.alert.*`; one `alert.evaluate` per matching `alert` subscription, dedup `alert:{event}:{subscription}`), `AlertEvaluateJobHandler` (raise: minimum severity, key, active alert read `FOR UPDATE`, occurrence or new row under the unique active-key index, maintenance windows, cool-down reopen; resolve by record or by key; publishes `platform.alert.*` through `EventWriter` with the subject record; never sends) and `AlertEscalateJobHandler` (completes its own job first, then locks the alert; stops scheduling when only steps that wait for acknowledgment remain on an acknowledged alert), plus the job that announces alerts held by a maintenance window when it ends (`alert.unsuppress`). `Alerts/AlertService.cs`: visibility (owners, assignee, `alerts.respond`; read access to the record, applied before paging; 404 otherwise), acknowledge, resolve and assign (refuse agents with `agent_not_allowed`, lock the row, check the version, audit `alert.<action>`, publish nothing while suppressed), maintenance windows (`alerts.manage` with fresh facts, at most 14 days, audited). `alert_owner` recipients (`NotificationJobs.cs`) resolve only for alert events with source `platform.alerts`. Never send messages from the alert service; never let an alert event raise an alert.
- Audit (ADR 0022): `AuditWriter` stays in the acting transaction; never compute or lock the hash chain in a business transaction (it would serialize each workspace and can deadlock with record locks). Only the definer functions touch chain state: `kernel.seal_audit` (worker), `kernel.verify_audit_chain` (workspace from the session context), `kernel.audit_verification_due` and `kernel.purge_retention` (migrations 0016 and 0017). Sealed rows are immutable (guard trigger, column-level `INSERT` without the chain columns): never map `chain_seq`, `prev_hash` or `hash` on `AuditRow`, read them with SQL. Purge only a sealed, re-verified prefix up to the verified point and before any break, and move the anchor in the same transaction. `Services/AuditMaintenance.cs` (`AuditMaintenanceService` in the worker): seal every 10 s, verify chains not verified in a day, purge hourly, report a break once (`audit.chain_broken`). `Services/AuditService.cs`: search (`audit.read`), export (`audit.export`, audited in its own transaction before the first byte, at most 400 days and 500,000 entries, CSV formula escaping), JSON Lines with chain links only for `permissions.admin`, details redacted for everyone else, chain status, Verify now (`audit.manage`, rate limited), retention (shortening also needs `permissions.admin`) and legal holds (`audit.manage`; released only by `permissions.admin` or the person who placed them); agents are refused everywhere.
- Mail (ADR 0023): `Mail/MailIntakeService.cs` receives a message once per mailbox and Message-ID (or content hash; unique index, races return the first row) and schedules `mail.process` (dedup `mail:{id}`) in the same transaction; processing locks the row and applies the guards in this order: no intake, unreadable, bad sender, own mail, RFC 3834 automatic mail, per-sender hourly cap, sender verification (`MailGuard.Verify`: only the topmost `Authentication-Results` of the mailbox's `authservId`, relaxed alignment), empty, membership. Never process mail as anyone but the sender (their own `RecordService` permissions, channel `email`) or, after an accept, as the sender only when the message was verified and otherwise as the reviewing person on the sender's behalf (unverified or unknown senders: a record with the claimed or named member as requester, thread replies as the reviewer's `work_note`); never set the requester field for a sender; only the requester's own reply is a `public_reply` (and only it reopens), any other member's emailed reply is their `work_note`. `MailProcessJobHandler.OnAbandonedAsync` marks a message `processing_failed` when retries run out. A reply's message is marked processed in the activity's transaction (`AddActivityAsync` `alongside`); creates use the idempotency key `mail:{id}`. The raw message is kept only until it is processed or decided (`kernel.purge_inbound_mail`: raw dropped after a day, rows after 30 days, never during a hold; reject drops it at once unless a legal hold is active). Review needs read-all and create on the intake's entity, mailboxes `notifications.manage` or `permissions.admin` (fresh facts; `senderVerification: none` needs `permissions.admin`); the per-sender cap counts processed mail only; agents are refused everywhere. `Mail/MailThreading.cs` finds records (delivery Message-ID, inbound Message-ID, `[NUMBER]`) and gives outbound email its Message-ID, `References` and `Reply-To`; finding a record never grants anything. `Mail/ImapPoller.cs` re-checks `AllowedImapHosts` on every poll, reads credentials only through secret references and stores error codes, never server text. `NotifyResolveJobHandler.ReplyAsync` feeds `{{activity.body}}` only from unredacted public replies and skips the reply's author. MailKit and MimeKit stay in this project (architecture test).
- AI providers (ADR 0024): `Assistant/AiCatalog.cs` is the operator's model catalog and named credentials (built from configuration by `Esmbler.Hosting.AiCatalogFactory`, never from workspace data): `Usable` = evaluated, credential configured for the entry's provider, and offered to the workspace (`AllowedTenants` by slug, for customer-paid keys); `Cost` prices uncached input, cache reads at a tenth, cache writes at 1.25 times and output, and an unknown model at the highest catalog prices; `MaxDailyBudgetUsd` (default 100) caps workspace budgets. `AiCredential` and the catalog must never put a key in `ToString()`, views, audit or logs; only the API host takes a credential to build a model client. `Assistant/AiSettingsService.cs`: `kernel.ai_settings` (one row per tenant: model, effort, daily budget, `allow_records_read`, external assistants `off`/`non_production`/`all`) and `kernel.ai_usage` (append-only usage with estimated cost), migration 0019, FORCE RLS; get and save only for `permissions.admin` (fresh facts for save), refused to agents; save locks the row `FOR UPDATE`, re-validates the choice, audits `ai.settings_save` with previous and new values (`environmentScoped: false`), and revokes the MCP connections the new policy disallows (off, production under `non_production`, `records:read` when no longer allowed: connection revoked, refresh tokens revoked, agent disabled); `ResolveAsync` re-validates a stored choice on every turn and falls back to the default; the budget is one per workspace across environments per UTC day.
- MCP connections (ADR 0025): migration 0020 adds `kernel.mcp_connections` (one row per consent: person, agent principal, client, environment, scopes, expiry, last use, revocation), `kernel.oauth_codes` and `kernel.oauth_refresh_tokens` (SHA-256 hashes bound to a connection), all FORCE RLS, and two definer lookups, `kernel.oauth_code_lookup` and `kernel.oauth_refresh_lookup`, that return only the tenant and environment of a 32-byte hash in an active workspace (on the definer allow-list in `Isolation.DatabaseIsolationTests`). The OAuth logic itself is `Esmbler.Hosting.Auth.OAuthService`; never add another way to reach these tables without a session.
- Events (ADR 0017): publish only through `EventWriter` in the caller's transaction; each consumer runs in its own tenant transaction and must be idempotent (inbox); a consumer that keeps failing dead-letters alone (queue `consumers` in `OperationsService`).
- Invariants: record change + audit + outbox in one transaction; queries filter by permission inside SQL; no secrets in audit details.
- Tests: `dotnet test tests/Esmbler.IntegrationTests` (needs Docker).
