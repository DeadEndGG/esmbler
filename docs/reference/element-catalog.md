Constraints:

- Always system and read-only: it cannot be set by the record API, imports, rules, or AI. Changing prefix affects new records only.

### Approval policy (`spec_object.approval_policy`)

Who must approve a request before fulfillment starts. Stages run in order; the approvers of one stage decide in parallel, and the stage passes when all of them approve (mode all) or when the first one approves (mode any). A stage can be conditional, expire, and escalate. Catalog items name the policy their requests use.

Constraints:

- id is unique; tenant policies start with tenant__.
- entity must be a request entity with an approval binding.
- 1–10 stages with unique snake_case IDs; each has 1–20 approvers of kind group (group key), role (role ID) or field (record.<field> or variables.<question> holding a user or group).
- mode is all or any; expiresAfterHours is 1–2160; onExpiry is reject or escalate, and escalate needs escalateTo and expiresAfterHours.
- when is a CEL-subset boolean over record and variables.
- The requester never approves their own request, and one person decides at most one step per stage.
- Approvals in flight keep the policy they started with; changing stages is a permission change.

Accessibility: role `none`; Not rendered directly; the approvals panel and the approvals inbox show its stages.

### Assignment rule (`spec_object.assignment_rule`)

Routes records to a group when a condition holds, such as sending network tickets to the Network queue. Rules are evaluated in order and the first match sets the entity's assignment group field (assignment_group on tickets). The group is named by key and resolved per tenant.

Constraints:

- when is a CEL-subset expression over record; group is a group key that must resolve to a group in the tenant, otherwise the rule is skipped with a warning.
- Evaluated in ascending order (ties by ID); the first matching enabled rule wins.
- Runs on create and when a field used in when changes, and only while the assignment group is empty or was set by an assignment rule — manual assignments are never overwritten.

Accessibility: role `none`; Not rendered directly.

### Catalog item (`spec_object.catalog_item`)

A requestable service offering, such as "New laptop" or "Software access". It defines typed questions (variables) the requester answers and the fulfillment tasks, with dependencies, that run once the request starts fulfillment. Requests are records of the item's requestEntity; tasks are records of that entity's task entity.

Constraints:

- id is unique; tenant items start with tenant__.
- requestEntity must declare a request binding.
- Variable keys are snake_case and unique; types are short_text, long_text, integer, decimal, date, date_time, single_select, multi_select, toggle, email, user or group; choice variables name a choice list.
- Task IDs are unique within the item; dependsOn names tasks of the same item and has no cycles; when is a CEL-subset boolean over variables and record.
- Deactivate items that requests still use instead of removing them.

Accessibility: role `none`; Not rendered directly; the catalog shows items as cards and the request form renders their variables.

### Choice list (`spec_object.choice_list`)

A reusable, ordered list of options for single_select, multi_select, status, and priority fields. Each option has a stable ID that records store, a label people see, an optional tone token for badges, and a hidden flag for retiring options without losing data.

Constraints:

- Option IDs are unique within the list, stable, and never reused; renaming an ID would orphan stored values.
- tone must be a design token (accent.red, accent.amber, ...), never a raw color.
- Retire options with hidden: true; they stay valid on existing records but cannot be newly selected.
- A list holds at most 100 options; order is display and sort order.

Accessibility: role `none`; Not rendered directly.

### Conditional rule (`spec_object.conditional_rule`)

A rule (RuleSpec, kind conditional) that changes how fields behave when a condition is true: require, show, hide, make read-only, set a value, restrict choice options, or show a message. With scope data it applies on every write path and drives the field rule hooks in all views; with scope form it only affects one view's presentation.

Constraints:

- kind is conditional; when is a CEL-subset expression (empty means always); actions has at least one entry.
- Action types: require, show, hide, read_only, set_value (value is an expression), restrict_options (options are IDs of the field's choice list), message (tone info, warning, or critical).
- Rules run in ascending order, ties by ID; a later set_value overwrites an earlier one. A data rule cannot require and hide the same field under overlapping conditions.
- Form-scoped hide and read_only are presentation only and never security controls.

Accessibility: role `none`; Not rendered directly.

### Entity (`spec_object.entity`)

A record type, such as Ticket or Vendor: its labels, the field that names a record (titleField), its fields, and the user/group fields that relate people to records for record-level access (accessFields). Entities are the backbone of every view, rule, workflow, and permission. Modules ship base entities; tenants add their own with IDs starting tenant__.

Constraints:

- id is unique in the effective configuration; tenant entities use tenant__<name>, module entities <module>.<area>.<name>.
- titleField must be a field of the entity of type short_text or auto_number.
- Field keys are unique within the entity; base keys contain no "__" and tenant-added keys start with tenant__.
- accessFields must reference user or group fields of the entity.
- Entities and fields are never physically removed from a published layer; they are hidden or deprecated so data is kept.

Accessibility: role `none`; Not rendered directly.

### Field definition (`spec_object.field_definition`)

The definition of one field of an entity (FieldSpec): a stable key, a field type (one of the field.<type> elements), a label, and the constraint props that apply to that type, plus flags such as required, readOnly, hidden, deprecated, and system. Views place fields with the field element; this spec defines what the field is everywhere.

Constraints:

- type must be one of the field types; type-specific props are validated against field.<type>'s propsSchema and props that do not apply to the type are rejected.
- key is unique within the entity and immutable; changing type means adding a new field and migrating with a convert migration (expand, backfill, contract).
- required and readOnly here are data-level and enforced on every write path; system fields are never writable through the record API.
- Fields are hidden or deprecated, never deleted, so existing values are kept.

Accessibility: role `none`; Not rendered directly.

### Form (`spec_object.form`)

A ViewSpec of kind form: a compact create or edit form for an entity, used for quick create dialogs (action.button with action quick_create:<view id>) and portal request forms. It holds only the fields needed at that moment plus a save button; data rules apply as on every write.

Constraints:

- kind is form; entity must exist; layout must be a layout.page node.
- Every required entity field without a default must be placed on the form.
- Referenced by quick_create:<id> actions; the viewer needs create permission on the entity.

Accessibility: role `none`; Not rendered directly.

### List view (`spec_object.list_view`)

A ViewSpec of kind list: the page for finding and working many records of an entity, typically saved views, a filter bar, and a data table with columns. Rows, counts, and columns are filtered by the viewer's permissions on the server.

Constraints:

- kind is list; entity must exist; layout must be a layout.page node.
- The layout must contain at least one collection.data_table for the view's entity.
- Node IDs are unique within the view and stable; props validate against each element's propsSchema.

Accessibility: role `none`; Not rendered directly.

### Notification template (`spec_object.notification_template`)

An email/in-app notification sent when a record event happens (record.created, record.transitioned, ...) to recipients named by user fields of the entity or the watchers. Subject and body are plain text with {{record.<field>}} placeholders, rendered per recipient with that recipient's permissions.

Constraints:

- Recipients are user field keys of the entity or the literal "watchers".
- Subject and body are plain text; HTML is escaped, never rendered. Placeholders must reference fields of the entity.
- Placeholders render with the recipient's field permissions; fields they cannot read render empty.
- Internal work notes are never included in notifications to requesters or portal users.

Accessibility: role `none`; Not rendered directly.

### Permission set (`spec_object.permission_set`)

Grants roles access: per entity (create, read and update scopes none/related/all, delete, optional ABAC update condition), per field (hidden, read, write), and platform actions (config.edit, audit.read, records.export, ...). Access is denied by default and grants from several sets combine.

Constraints:

- read and update are none, related, or all; related uses the entity's accessFields.
- Field access is hidden, read, or write; field "*" covers all fields and a specific field entry overrides it within the set.
- Across sets grants combine as a union (most permissive wins); hidden fields are never sent to the client.
- actions must be platform actions; updateCondition is a CEL-subset expression over record and user.

Accessibility: role `none`; Not rendered directly.

### Record view (`spec_object.record_view`)

A ViewSpec of kind record: the page for viewing and editing one record of an entity. Its layout is a tree of nodes rooted at layout.page, built from registry elements (sections, rows, columns, cards, fields, activity, actions). Node IDs are stable so overlays can insert, move, and hide nodes across upgrades.

Constraints:

- kind is record; entity must exist; layout must be a layout.page node.
- Node IDs are unique within the view and never reused; every node's type must be a registry element and its props must validate against that element's propsSchema.
- Every parent/child pair must be allowed by the registry; row spans must sum to 12.

Accessibility: role `none`; Not rendered directly.

### Relationship (`spec_object.relationship`)

Describes a lookup between two entities in both directions: the many-to-one side stored in a lookup field (a ticket's parent) and the one-to-many inverse shown in related lists (a ticket's child tickets). It also states what happens to referencing records when a target is deleted.

Constraints:

- field must be a lookup field on entity whose target equals target; each lookup field has exactly one relationship.
- kind is lookup in Gate 1; onTargetDelete is restrict (block deleting targets with children) or clear (null the lookup).
- Self-relationships may not form cycles; a write that makes a record its own ancestor is rejected.
- Relationships never grant access: each side is filtered by the viewer's own permissions.

Accessibility: role `none`; Not rendered directly.

### Role (`spec_object.role`)

A named job function, such as Agent or Requester, that people hold in a tenant. Roles carry no permissions themselves: permission sets grant access to roles, and workflow transitions can be limited to roles.

Constraints:

- id is unique and stable; tenant roles start with tenant__.
- A role grants nothing until a permission set lists it.
- Roles are assigned to members and groups in tenant administration, not in specs.

Accessibility: role `none`; Not rendered directly.

### Validation rule (`spec_object.validation_rule`)

A rule (RuleSpec, kind validation) that blocks a write unless its assert expression is true, with a message shown on a field. With scope data (the default) it runs on every write path — UI, API, imports, automations, and AI. Optional when limits it to records where a condition holds.

Constraints:

- kind is validation; assert is required and must be a boolean CEL-subset expression over record and user that type-checks against the entity.
- message is required; field, when set, must be a field of the entity. Validation rules have no actions.
- Expressions are side-effect free with bounded cost; rules run in ascending order, ties broken by ID.
- scope form requires view and applies only in that view; it is never a security control.

Accessibility: role `none`; Not rendered directly.

### Workflow (`spec_object.workflow`)

The state machine of an entity: its states (each in a category such as active or resolved), the initial state, and the transitions between them, with guards, required fields, role restrictions, field values set on firing, and button tone. The workflow owns the entity's status field, which changes only through transitions.

Constraints:

- stateField must be the entity's status field; its choice list option IDs must equal the state IDs.
- initialState and every from/to must be states of the workflow; every state must be reachable from initialState.
- guard is a CEL-subset expression; requiredFields and set keys must be fields of the entity and set may not target the status or system fields.
- Each published change to the state field, initial state, states or transitions registers a new definition version; activeInstances decides whether running records stay pinned, migrate through stateMap, or move to cancelState (ADR 0015).

Accessibility: role `none`; Not rendered directly.
