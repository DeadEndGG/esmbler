# ADR 0002: Storage and query model

## Context and problem statement

Every tenant customizes entities with its own fields (up to 200 custom fields per entity), while modules ship their own fields. The pilot targets 10 tenants with up to 500,000 tickets each, pooled in one database. The master spec ("Multi-tenancy", "Record ownership, queries") asks us to choose a physical layout for custom fields, decide whether per-tenant index DDL is allowed, define a typed, bounded query contract, and apply authorization before paging and counting.

Where do record values live, and how are they queried safely?

## Decision drivers

- No tenant-specific DDL on the hot path: an AI-added field must publish in seconds without a schema migration.
- One isolation mechanism (RLS) for every record, regardless of module.
- Permission predicate applied before `ORDER BY`, `LIMIT` and `COUNT` ([ADR 0004](0004-authorization-engine.md)).
- Bounded query cost per tenant; no query can scan the whole table.
- Precise types: decimals, UTC instants vs local dates, null vs absent, stable choice IDs.

## Considered options

1. **Shared `kernel.records` table, all fields in `data jsonb`** (module and custom alike).
2. Typed extension tables per entity with generic columns (`str_01..str_50`, `num_01..`).
3. EAV (`record_values(record_id, field_key, value_*)`).
4. Per-tenant columns or per-tenant tables (`ALTER TABLE` on publish).
5. Schema per tenant.

## Decision outcome

**Chosen option 1.** One PostgreSQL 18 database, schema `kernel`, pooled tenants. Values are keyed by field key in `data`. No per-tenant DDL in the pilot, including controlled index DDL.

### Table sketch

```sql
CREATE TABLE kernel.records (
  tenant_id       uuid        NOT NULL,
  environment_id  uuid        NOT NULL,
  id              uuid        NOT NULL,            -- UUIDv7, generated by the record engine
  entity_id       text        NOT NULL,            -- e.g. 'core.tickets.ticket'
  number          bigint,                          -- auto-number (kernel.record_sequences)
  revision        integer     NOT NULL DEFAULT 1,  -- optimistic concurrency
  data            jsonb       NOT NULL,            -- {"title": "...", "tenant__vendor": "..."}
  config_revision integer     NOT NULL,            -- config the last write was validated under
  search          tsvector,                        -- maintained by the record service from fields no permission set hides
  created_at      timestamptz NOT NULL DEFAULT now(),
  created_by      uuid        NOT NULL,            -- principal ID (the agent, if any, is in kernel.audit_log)
  updated_at      timestamptz NOT NULL DEFAULT now(),
  updated_by      uuid        NOT NULL,
  deleted_at      timestamptz,
  PRIMARY KEY (tenant_id, environment_id, id)
);
ALTER TABLE kernel.records ENABLE ROW LEVEL SECURITY;
ALTER TABLE kernel.records FORCE ROW LEVEL SECURITY;  -- policy in ADR 0010
```

The authoritative definition is `packages/Esmbler.Kernel.Infrastructure/Migrations/0001_kernel.sql`.

### Indexes (shared, created by platform migrations only)

| Index | Definition | Serves |
|---|---|---|
| Primary key | `(tenant_id, environment_id, id)` | Point reads, updates |
| List | btree `(tenant_id, environment_id, entity_id, updated_at DESC) WHERE deleted_at IS NULL` | Default sort |
| Number | unique `(tenant_id, environment_id, entity_id, number)` | Lookup by ticket number (`TCK-42` in search) |
| Containment | GIN `data jsonb_path_ops` | Equality on choice, user, group, lookup, toggle; multi-select contains; permission predicate on `requester`/`assignee` |
| Full text | GIN `search` | `search` term in the query contract |

### Value encoding in `data`

| Field type | JSON encoding | Notes |
|---|---|---|
| short/long text, email | string | Rich text stored sanitized (threat model, XSS) |
| integer, decimal | number | jsonb numbers are PostgreSQL `numeric`, so no binary rounding; scale enforced on write |
| date | `"2026-10-10"` | Local date, no zone |
| date-time | `"2026-10-10T14:03:00Z"` | Always UTC, fixed format so text order equals time order |
| single select, status, priority | option ID string (`"access"`) | Labels never stored |
| multi-select | array of option IDs | |
| user, group, lookup | UUID string | Lookup = relationship to another record |
| absent key vs `null` | absent = never set; `null` = explicitly cleared | Both read as `null` in expressions ([ADR 0009](0009-rule-expression-language.md)) |

Auto-numbers use `kernel.record_sequences (tenant_id, environment_id, entity_id, next_value)` with `UPDATE … RETURNING`, not database sequences (sequences are DDL). The value is stored in the `records.number` column.

### Typed query contract

Clients never send SQL. A query is `{entity, filters, search, sort, offset, pageSize}` (`RecordQuery` in `packages/Esmbler.Kernel.Infrastructure/Records/QueryCompiler.cs`). Each filter is a CEL-subset expression checked against the entity schema, then compiled to parameterized SQL with type-aware casts. The permission predicate from the PDP is ANDed in before ordering, paging and counting.

Request:

```json
{
  "entity": "core.tickets.ticket",
  "filters": ["record.status in ['new', 'assigned'] && record.priority == 'p1' && record.tenant__vendor_score >= 3"],
  "sort": { "field": "priority", "descending": false },
  "offset": 0,
  "pageSize": 50
}
```

Generated `WHERE` and `ORDER BY` (user `sam`, member of group `service_desk`; RLS context already set per [ADR 0010](0010-database-migrations-and-roles.md)):

```sql
WHERE r.entity_id = $1 AND r.deleted_at IS NULL
  -- permission predicate (read scope "related": one clause per entity access field)
  AND ((r.data->>$2) = $3                  -- requester = sam
       OR (r.data->>$4) = $5               -- assignee = sam
       OR (r.data->>$6) = ANY($7))         -- assignment_group in sam's groups
  -- user filter
  AND (((r.data->>$8) = ANY($9))                                      -- status in [...]
       AND COALESCE(((r.data->>$10) IS NOT DISTINCT FROM $11), false)  -- priority == 'p1'
       AND COALESCE(((r.data->>$12)::numeric >= $13), false))          -- vendor score >= 3
ORDER BY array_position($14, r.data->>$15) ASC NULLS LAST, r.id      -- choice option order
```

Compiler rules: `==` compiles to `IS NOT DISTINCT FROM` and `!=` to `IS DISTINCT FROM`; every boolean sub-expression is wrapped in `COALESCE(…, false)`, so null behaves exactly as in the expression language, including under `!`. Comparisons with `null` are false. Choice fields sort by option order, not label. Filtering on a field hidden from the caller is rejected (`invalid_filter`), so a filter cannot probe hidden values through result membership or counts; a hidden sort field falls back to the default sort (`updated_at DESC`). Unsupported constructs return `unsupported_filter`. Search matches the `search` tsvector (`websearch_to_tsquery('simple', …)`) or, for input like `TCK-42`, the `number` column.

### Query limits at pilot scale

The compiler defines `MaxPageSize = 100`, `MaxOffset = 10000` and `MaxFilterNodes = 64` (filter length 1,000 chars, depth 16). `RecordService.QueryAsync` (used by the list API and the MCP tools) enforces them.

| Limit | Value | Status |
|---|---|---|
| Page size | default 25, max 100 | enforced (clamped) |
| Filter size | 64 nodes, 1,000 chars, depth 16 per filter | enforced (`invalid_filter`) |
| Sort keys | 1 | enforced by the query shape |
| Offset paging | offset ≤ 10,000 | enforced (clamped) |
| Count | exact up to 10,000, then capped (`total` = 10,000 with `totalIsCapped: true`) | enforced |
| Statement timeout | 5 s per list query (`SET LOCAL statement_timeout`) | enforced; a timeout is not yet mapped to a dedicated `query_timeout` error |
| Relationship traversal in filters | none in Gate 1 (filter lookups by ID) | enforced (`unsupported_filter`) |
| Export | async job, `records.export` action | planned (Gate 2) |

Targets at 500k tickets and 200 custom fields per tenant: list p95 < 300 ms for indexed filters. `Records.QueryBenchmarkTests.List_queries_meet_the_latency_budget_at_100k_tickets` checks the budget in CI at 100k tickets with the permission predicate in SQL. Range filters and sorts on custom fields have no index: they scan the permission-filtered (tenant, environment, entity) slice and are bounded by the timeout.

### Custom-field index policy

- No per-tenant indexes, columns or tables. Platform migrations own every index.
- The shared GIN index (`jsonb_path_ops`) serves containment (`@>`) predicates. The compiler emits `->>` comparisons, which it does not use; switching scalar equality to `@>` where null semantics allow remains an option if the benchmark regresses (the restrict check on delete already uses `@>`).
- A field is searchable only if no permission set hides it: the record service builds the `search` tsvector from those fields only, so full-text search cannot leak hidden values.

### Soft delete, integrity and concurrency

Implemented in `RecordService` (`packages/Esmbler.Kernel.Infrastructure/Records/RecordService.cs`) on top of the write pipeline (`RecordWriteEngine`).

- **Soft delete:** sets `deleted_at` and bumps the revision (the actor is in `kernel.audit_log`, and a `record.deleted` event is written). `POST /api/records/{entity}/{id}/restore` clears it within 30 days for anyone allowed to delete the record (`restore_expired` after that, [ASM-027](../decisions/assumptions.md)); purge is a Gate 2 retention job. Deleting a record referenced by a non-deleted record through a `restrict` relationship fails with `409 has_children` and the referencing count. The count is not yet limited to records the caller can see.
- **Revision:** every update is `UPDATE … SET revision = revision + 1 WHERE … AND revision = $expected`. Zero rows means `409 record_conflict` with the current revision and the fields changed since the client's revision (from audit). There is no silent server merge; the renderer re-applies non-overlapping edits and asks the user about overlapping ones.
- **Idempotency:** commands may carry `Idempotency-Key`. The key row is written in the same transaction as the record.

```sql
CREATE TABLE kernel.idempotency_keys (
  tenant_id uuid NOT NULL, environment_id uuid NOT NULL,
  key text NOT NULL,
  principal_id uuid NOT NULL,
  request_hash text NOT NULL,          -- sha256 of method + route + canonical body
  response jsonb NOT NULL,             -- replayed verbatim on retry
  status_code integer NOT NULL,
  created_at timestamptz NOT NULL DEFAULT now(),  -- 24 h retention intended; no cleanup job yet
  PRIMARY KEY (tenant_id, environment_id, key)
);
```

The same key with a different body, or from another principal, returns `422 idempotency_key_reused`; a matching retry replays the stored response. Concurrent retries of one key are serialized with a transaction-scoped advisory lock instead of returning `409 idempotency_in_progress`. Verification: `Records.RecordServiceTests.Idempotency_key_replays_the_same_result`, `Records.RecordServiceTests.Create_update_conflict_and_history`, `Records.RecordServiceTests.Deleted_records_can_be_restored_by_people_who_may_delete_them`.

### Consequences

- Good: publishing a field is a metadata change; tenant isolation is one RLS policy; module and custom fields behave the same.
- Bad: no per-field statistics, so the planner misestimates selective custom filters; range and sort on custom fields degrade linearly with slice size.
- Bad: type safety lives in the record engine and migrations, not in column types.

## Pros and cons of the options

| Option | Pros | Cons |
|---|---|---|
| JSONB in shared table | No DDL; one RLS policy; GIN covers equality | Weak planner stats; range/sort unindexed |
| Typed extension tables | Real btree per slot | Slot allocation per tenant; joins; slot exhaustion at 200 fields |
| EAV | Flexible | One row per value (100M rows at pilot scale); every filter is a self-join |
| Per-tenant columns/tables | Native types and indexes | DDL on publish; locks; migrations per tenant; RLS per table |
| Schema per tenant | Strong isolation | Thousands of objects; migrations × tenants; pooled connection churn |
