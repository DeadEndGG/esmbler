# Tickets module (core.tickets)

Default Tickets/Service Requests module and the reference implementation of a module built only on the public SDK.

- Owns entities `core.tickets.ticket`, `core.tickets.request` and `core.tickets.request_task` (1.2.0), choice lists `core.tickets.*`, workflows `core.tickets.lifecycle|request_lifecycle|task_lifecycle`, views `core.tickets.record|list|quick_create|request_record|request_list|task_record|task_list`, catalog items `core.tickets.catalog.*`, approval policies `core.tickets.approval.manager|access` (1.3.0), roles agent/requester/admin and approver (1.3.0, `TicketsIds.ApproverRole`), business calendar `core.tickets.calendar.business_hours` and SLA policies `core.tickets.sla.ticket|request|task` (1.5.0, ADR 0018), metrics `core.tickets.metric.*` and the dashboard `core.tickets.dashboard` (1.6.0, ADR 0019), and notifications (1.7.0, ADR 0021): subscriptions `core.tickets.sub.escalated|p1_raised`, templates `core.tickets.template.escalated|p1_raised` and routes `core.tickets.route.escalated` (assignee and assignment group, built-in profile `core.platform.profile.in_app_email`) and the mandatory `core.tickets.route.p1_raised` (same recipients, `core.platform.profile.urgent`). Notification IDs stay in the `core.tickets.` namespace and routes reference only the module's own elements or `core.platform`. The Gate 1 templates (`core.tickets.notify.*`) keep their own triggers (legacy, `NotificationConsumer`). SLA alerts (1.8.0, ADR 0022): alert subscriptions `core.tickets.sub.sla_breached_alert|sla_warning_alert|ticket_done_alert`, alert rules `core.tickets.alert.sla_breached` (owner `field:assignment_group`, key `record.id + ':' + event.target`, escalates after 30 minutes unless acknowledged) and `core.tickets.alert.sla_at_risk` (resolved by the breach too), notification subscriptions `core.tickets.sub.sla_alert_opened|sla_alert_escalated`, template `core.tickets.template.sla_alert` and the optional routes `core.tickets.route.sla_alert_opened|sla_alert_escalated` (recipients `alert_owner`). Alert rules use only the module's own subscriptions.
- Releases: `Esmbler.Modules.Tickets/Releases/<version>/module.json` (1.0.0 to 1.8.0: 1.6.0 metrics and the Overview dashboard, 1.7.0 notification routes, 1.8.0 SLA alerts). Shipped releases are immutable; changes go in a new version with declarative migrations.
- Extension points: `core.tickets.hooks.before_write`, `core.tickets.hooks.after_write`, `core.tickets.strategy.assignment`, `core.tickets.slots.record_side_panel`.
- Events published: by the record engine, `record.created|updated|transitioned|deleted|restored` and `activity.added` for each entity; declared by the module (1.4.0, ADR 0017), `core.tickets.ticket.escalated` (transition `escalate`), `core.tickets.ticket.priority_raised` (rule `core.tickets.rules.p1_raised`, when a ticket becomes P1) and `core.tickets.ticket.resolved` (transition `resolve`). Event type IDs stay in the `core.tickets.` namespace (validator). Request fulfillment (task creation, release, completion) is platform behavior driven by the request binding (`FulfillmentConsumer`, ADR 0015), not module code; so are approvals (`ApprovalService`, ADR 0016), declared by the binding's `approval` block and the catalog items' `approvalPolicy`.
- Invariants: reference only `Esmbler.Sdk` and `Esmbler.Modules.Tickets.Contracts`; no package references.
- Tests: `dotnet test tests/Esmbler.UnitTests --filter FullyQualifiedName~Configuration`. Docs: `docs/architecture/modules/tickets.md`.
